Scanner reports in. Structured findings out.

Vulnerability scanners hand you a PDF: hundreds of findings, each vendor with its own layout and vocabulary. MulitaMiner reads that PDF, isolates every finding, lets an LLM fill one shared record schema, and gives you back one row per vulnerability, with name, severity, CVSS, host, port, solution and references, ready for a spreadsheet, a ticket tracker or a risk queue.

How it works

Five stages. The LLM only touches one of them.

Segmentation decides how many findings there are before any model call, so a finding can be extracted badly, but never silently lost. Click a stage to inspect it.

Read. The PDF text is extracted page by page (pypdfium2) and cleaned: headers, footers and page numbers that would otherwise split a finding in two are removed.

Nothing is OCR'd; scanner exports are born digital.

Segment. A scanner profile is a JSON file with the regular expression that opens a finding in that vendor's layout (for OpenVAS, a severity line followed by NVT:) and where the host and port live. The profile cuts the text into blocks, one per finding, and numbers them.

No LLM is involved, so the count is exact and repeatable. Adding a scanner means adding one JSON file.

Extract. Blocks are packed into token-budgeted chunks and sent to the model with the scanner's prompt and a JSON schema derived from the record type. The model must return exactly one record per block id.

Missing ids are re-sent in smaller groups (4, then 2, then 1); unknown or duplicate ids are dropped with a warning. Every drop is declared in the run log, never silent.

Consolidate. Records that belong to the same finding (one vulnerability on several ports, or a scanner that splits a finding across pages) are paired and merged. Severity labels and CVSS are normalised, references deduplicated.

The pre-consolidation records are kept, so every merge decision can be audited.

Export. The same records serialise to XLSX and CSV for people, and to SARIF 2.1.0, CSAF 2.0, DefectDojo Generic JSON and CAIS for tools. The web demo offers the first two; the CLI has all six, plus a KEV/EPSS/SSVC remediation queue.

Research

Four papers, one pipeline.

MulitaMiner is a research project at UNIPAMPA. Each version of the tool was evaluated against hand-curated ground truth and published.

Structured Extraction of Vulnerabilities in OpenVAS and Tenable WAS Reports Using LLMs

The first method: an LLM turns OpenVAS and Tenable WAS findings into a standard format for risk management. On 34 vulnerabilities, GPT-4.1 and DeepSeek came closest to the baseline (ROUGE-L above 0.7).

MulitaMiner: A Multi-Version Evaluation of LLM-Based Vulnerability Report Extraction

Three versions of the pipeline (functional baseline, scanner-aware segmentation, per-LLM tuning with few-shot prompts) over 450 runs with five LLMs. Exact record match rises from 37.5% to 90.4% and omission falls from 20.5% to 1.7%: pipeline engineering, not model substitution, is the lever.

On-Premise vs. Cloud: Local LLMs for Vulnerability Extraction from Security Scanner Reports

A scan report maps an organisation's attack surface, so sending it to a cloud API trades confidentiality for accuracy. Nine local models (4B to 21B) against a DeepSeek reference: the best local model, on a consumer GPU, trails the cloud by 1.2 points in free-text fidelity and matches it on structured fields. The fine-tuned 1.5B model in the repository comes out of this line of work.

Or keep everything local

MulitaMiner is a CLI first. Install it, point it at a local model (Ollama, LM Studio, any OpenAI-compatible server) and nothing leaves your network. The same web interface runs locally with Docker Compose, with the fine-tuned model included.
